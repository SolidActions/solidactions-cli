# CLI doc commands on the current MCP catalog (cli#151) — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to carry out this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking. Subagents are Sonnet or better, never Haiku.

**Goal:** `solidactions doc push` and `doc pull` call the current MCP tools again (they fail today with "Tool [docs_vault] not found"), and a live test against the dev stack pins `doc push`, `doc pull` and `doc upload` so a catalog rename can't silently break them again.

**Architecture:**
- All docs MCP calls go through `callDocsTool` in `src/utils/mcp.ts`. Same pattern as #150's `resolveCrewsCall`: a route table keyed on the action picks the public tool. `callDocsTool(config, args)` drops its tool-name argument; the tool comes from `resolveDocsCall(args)`, which throws for an action with no route.
- Call sites send the **public** action names, so no action or param renaming is needed.
- `doc upload` uses REST (`POST /api/v1/docs/media`), not MCP. It needs no code change, only the live test.

**Server facts** (solidactions-app `origin/main` b4631b63b, `app/Mcp/Catalog/ToolCatalog.php:11-38`, confirmed live on sa-dev with `action: describe`):

| CLI call site | Retired | Current tool / action | Params the server accepts |
|---|---|---|---|
| `doc-pull.ts` listTree | `docs_vault list` | `docs_read list` | `folder_path` |
| `doc-pull.ts` fetchBodies | `docs_vault bulk_read` | `docs_read bulk_read` | `items` (required) |
| `doc-pull.ts` single-doc fallback | `docs_vault read` | `docs_read read_doc` | `id`, `path` |
| `doc-push.ts` untracked files | `docs_vault bulk_create` | `docs_manage bulk_create` | `folder_path`, `parse_frontmatter`, `type`, `client_request_id`, `items` (required), `on_conflict`, `dry_run` |
| `doc-push.ts` tracked files | `docs_edit write` | `docs_manage write` | `id`, `body` (required), `properties`, `enforce_required`, `base_revision` |

No renamed params for these actions. Response bodies are the source tool's, unchanged. Cleanup: `docs_delete delete_folder {id}` soft-deletes a folder and everything in it. `docs_read list` returns `{folders: [{id, name, folder_path, ...}], docs: [...]}`.

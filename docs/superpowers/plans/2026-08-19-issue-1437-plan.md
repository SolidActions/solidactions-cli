## Ask (issue body + cli#118)
- Warn when the CWD-inferred workspace differs from the last-used one (per-user state file).
- Require confirmation (or explicit `-w`) for CWD-inferred **writes**. Reads stay frictionless.
- Print the resolved workspace (org-prefixed, per #1194) on every mutating command's first output line.
- Tests in the CLI repo. Close cli#118 with the same PR reference.

## Design (implemented)
"CWD-inferred" == `resolveConfig().sources.workspaceId` is a filesystem path that is NOT the global
config path (i.e. a `.solidactions/config.json` found by walking up from CWD). Guard fires on **change**:

| resolution source | last-used | read | write |
|---|---|---|---|
| `-w` / env / global config | any | — | — |
| CWD-inferred | none recorded, or same | — | — |
| CWD-inferred | **differs** | warn (stderr) | confirm; `--yes` or `-w` skips; non-TTY refuses exit 1 |

## Defect found by live smoke after Task 4 (Task 5)

**A harmless read disarms the write guard.** `src/utils/api.ts` (~496) called
`writeLastUsedWorkspace` unconditionally for every command that resolves a workspace, reads
included. So a read RECORDS the newly-inferred workspace as last-used, and the next write in that
directory sees "last used == resolved" and skips the guard outright.

Reproduced live against the dev stack (CWD pinned to `production`/Acme Corp, last-used
`test-workspace`):

| sequence in `acme-proj` | result |
|---|---|
| `env set demo KEY VALUE` alone | warn + refusal, **exit 1** — guard works |
| `project list` then the SAME `env set` | **no warn, no confirm, no refusal** — the write proceeds against production |

That second row is the exact production failure the issue was filed for ("look around, then
write"), and the read's warn goes to stderr, which scripted/AI callers drop. Fix: record last-used
**only for mutating commands**, so `state.json` means "the workspace you last WROTE to" — precisely
what the write confirmation compares against. Refused/declined writes already throw before the
record and must keep doing so.

Folded into the same task, from the Task 3 re-review:

  filter was removed.

## Second defect found by live smoke (Task 6)

**The guard's own refusal hint advertised a flag most commands don't have.** The non-TTY refusal
printed `… or --yes to accept the inferred one`, but `--yes` is not global — `setAssumeYes`
(`src/index.ts:125`) reads the ACTIVE COMMAND's own flag, and most mutating commands never declare
one. Proven live:

    $ solidactions project create smoke-c --yes
    error: unknown option '--yes'          # exit 1

So the CLI blocked the write, told the caller exactly how to proceed, and the instruction failed —
in the branch of the guard that exists specifically to serve scripted/AI callers. `-w <id>` was
verified to work in trailing position on a command that doesn't declare it, so only the `--yes`
half was wrong.

Fix (`ae12d1a`): `setSupportsAssumeYes`/`getSupportsAssumeYes` mirror the existing assumeYes pair;
the preAction hook detects `actionCommand.options.some(o => o.long === '--yes')`; the hint appends
the `--yes` clause only when true. **Rejected: adding a global `--yes`** — new CLI surface this
issue didn't ask for, giving `--yes` a meaning on ~60 commands that never had one. The hint was
what was wrong, so the hint got fixed. Verified live, both variants:

    project create     -> re-run with -w <id> to confirm the target workspace
    database delete    -> re-run with -w <id> to confirm the target workspace, or --yes to accept the inferred one

## Decision ledger

- **Split PRs.** CLI fix = `solidactions-cli` PR; app repo gets a docs-only companion PR, because
  `scripts/issue park` validates `--pr` against `solidactions-app` only. Precedent: #1194, #1293.
- **Guard on CHANGE, not on inference alone.** Confirm fires only when a CWD-inferred workspace differs
  from a recorded last-used one, so the normal same-project workflow stays prompt-free and `-w`/env/
  global-config sources never prompt. *Cost if wrong:* a first write in a new directory prompts once.
- **Unclassified commands default to MUTATING** (fail-safe) so a newly added command can never silently
  skip the guard. *Cost if wrong:* an unclassified read gets a needless prompt (this is what happened
  to the hidden `skill run`).
- **`database pull` is MUTATING** (safe over-inclusion) because `--writable` runs a live SQL REPL;
  classification is command-path-only, so any command writable under ANY flag is classified mutating
  wholesale. Rejected flag-aware classification: machinery for one command.
  *Cost if wrong:* one needless prompt on a plain read-pull after a workspace change.
- **Banner to stderr** (from live smoke): on stdout it corrupts `--json` for script/AI consumers.
  *Cost if wrong:* stdout redirected to a file won't capture the banner — desirable for advisory output.
- **`workspaceOrg` travels with `workspaceId`'s layer**, never picked independently.
  *Cost if wrong:* a wrong org name in the banner — exactly the confusion #1194 fixed.
- **The handoff's "restore those two test files byte-identical" instruction was itself wrong** and was
  correctly not followed: their original assertion was `stderr === ''`, and the banner now lands on
  stderr by design, so stderr can no longer be empty.
- **`state.json` records the last workspace WRITTEN to, not merely resolved** (Task 5, found by live
  smoke): recording on reads let a harmless `project list` disarm the very next write's confirmation
  — the exact "look around, then write" production failure the issue was filed for.
  *Cost if wrong:* reads in a changed directory keep warning until you write there, which is
  advisory stderr and true.
- **The refusal hint offers `--yes` only when the command declares it** (Task 6, found by live smoke);
  **rejected adding a global `--yes`** — new CLI surface the issue didn't ask for, on ~60 commands
  that never had one. *Cost if wrong:* those commands' only non-interactive remedy is `-w <id>`,

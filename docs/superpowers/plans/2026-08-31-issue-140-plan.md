# Issue #140 — `dev --env` database-credential parity + discoverability

Branch: `issues/github-140` · Worktree: `__worktrees/issues/github-140`
Tier: standard-ish (issue-manager lane: Opus). Repo: SolidActions/solidactions-cli.

## Scope (issue body + ALL comments; newest comment wins)

1. `solidactions dev <file> --env <env>` must ALSO resolve mapped
   workspace-database credentials — same `{url, token, name, read_only}` JSON
   envelope `RuntimeEnvBuilder` injects into sandboxes. Short-TTL, IN-MEMORY
   only. `env pull` must NOT gain DB creds (deliberate: no credentials on disk).
2. `database --help` cross-reference note → `env map` + `dev --env`; clarify
   `import` = bulk data loading only.
3. ai-examples: copy-paste-runnable Drizzle examples — (a) connect (parse mapped
   DB env JSON → `createClient({url, authToken})` → `drizzle`), (b) a drizzle-kit
   migration setup running via `dev --env` / a workflow.
4. (Added 2026-09-01) `env pull` must EXPLAIN absent DB credentials, not silently
   skip: a CLI note per mapped-DB var AND a comment line in the written `.env` at
   that variable's position. Both must END with the copy-pasteable hint
   `To run locally with live platform vars + this database: solidactions dev <your-workflow-file> --env <env>`
   with the ACTUAL pulled env name substituted.

## Decision ledger

- **DECISION: no companion app PR.** `dev --env` mints through the EXISTING
  `POST /api/v1/databases {operation:'access', name, mode}` control plane
  (`HandleCliDatabaseOperation::issueAccess`), already wrapped CLI-side by
  `requestDatabaseAccess()` in `src/utils/database-data-plane.ts`. Rejected
  adding `resolve_databases=true` to `GET /projects/{slug}/variable-mappings`:
  that route is gated on `env:read`, so it would let an env-only token mint
  database credentials — a real privilege escalation past
  `databases:read`/`databases:edit` + `AccessService::canUse(Section::Databases)`
  + WriteFuse/DatabaseReadGate + the 20/min mint rate limit. The legacy
  `routes/api.php:522` env-resolve route stays untouched (superseded, #429).
- **DECISION: mint `write` first, fall back to `read`.** Parity with
  `RuntimeEnvBuilder`, whose authorization is `WriteFuse::authorizationFor()`
  (full-access unless the fuse degraded). Write mode is also what deliverable 3's
  drizzle-kit migrations need. `read_only` is set from the mode actually granted.
- **DECISION: TTL is the endpoint's 600s floor** (`duration_seconds`
  `between:600,86400`; omitted ⇒ 600). Also keeps the mint under the
  `>600s ⇒ service-credential` gate.
- **DECISION: a DB-resolution failure warns, it does not fail the run** — same
  posture as the existing dropped-var / dropped-secret reporting in `runDev`.
- **DECISION: examples land in SolidActions/solidactions-examples** (the surface
  `solidactions ai examples` actually reads) — companion PR ex#34.
- **DECISION: this PR does NOT repin `EXAMPLES_REF`** (reverses the earlier plan
  to repin here). The pin must name a MERGED examples mainline SHA — its own doc
  comment and the standing #1146 release contract both say so — and ex#34 is not
  merged. Pinning to a branch SHA that can be rebased or force-pushed away would
  make `init` and `ai examples` fetch a ref that may cease to exist, and
  `smoke:init` serves template content at exactly this ref. The repin belongs
  with the ex#34 merge or the next release ritual. Flagged in the PR body + park
  report as the one follow-up.
- **DECISION: `database --help` names the solidactions.yaml `database:`
  declaration, not Peter's literal `env map` wording.** `env map` maps GLOBAL
  VARIABLES (`<project> <key> <global-key>`) and has no `--database` flag; the
  project-level database mapping is a YAML declaration synced by
  `project deploy`. Pointing an agent at a nonexistent flag would reproduce the
  exact dead end this issue exists to fix.
- **DECISION: `ctx.vars.<DB>` carries a `DatabaseVar` OBJECT in dev, not the raw
  JSON string.** `dev-shim.mjs` builds `InvokeCtx` directly and never runs the
  SDK's `context-adapter`, which is what parses RuntimeEnvBuilder's JSON env
  string into `{name, url, token, readOnly}` for a deployed sandbox. Injecting
  the string would give local workflows a string where deployed gives an object
  — breaking `createDatabaseClient(ctx.vars.DB)` and `.readOnly` locally, i.e.
  the opposite of the parity this issue asks for.
